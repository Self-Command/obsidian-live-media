# 备份、日志与条件恢复

默认输出是副本，不修改文章引用。只有主动选择 `compression.output=replace` 并确认该批次，才替换原路径、名称和扩展名。

## 替换顺序

1. 再次读取原文件，对比预览时的 SHA256。
2. 写入 `.live-media-backups/<交易ID>/<原路径>`，读回校验原件指纹。
3. 在 `.live-media-reports/` 保存交易记录和索引。
4. 写入之前再次检查源指纹；保存候选结果；读回校验输出指纹。
5. 配对组先校验所有成员及备份，再串行提交。失败时只恢复仍匹配本插件输出指纹的成员。

目录名称可以在设置中修改，必须使用合法库内路径，不能混用输出、备份和报告目录。隐藏文件使用 DataAdapter，不创建业务笔记。

## 恢复方式

运行“检查日志并恢复原件”。

- **恢复**：备份指纹正确，当前源仍等于本插件输出时才覆盖；源已经是原件则只修正状态。
- **导出原件副本**：若当前文件已被用户修改、读回损坏或不同步，保存校验过的备份到新的同扩展名路径。已有路径一律拒绝覆盖。原文件和现有修改保持原样。
- 备份损坏、日志损坏或指纹不符会报告并停止；不猜测覆盖，不把未知记录当作空历史。

启动时只提示未完成交易，不自动继续压缩或恢复。`manual-days` 只标明哪些备份达到保留天数；没有后台删除。

## 取消与同步边界

临时编码阶段取消会终止 Worker／本机子进程，不写入原件。提交阶段停止剩余队列；已开始的配对组会完成或进行条件回滚，避免主动留半组。

Obsidian DataAdapter 没有跨设备原子 compare-and-swap。插件在写入前重复核对指纹，但不能阻止其他同步程序恰好在最后检查之后同时写入。首轮替换验收应在独立测试库进行；发生冲突保留备份，选择导出原件副本后人工比较。

副本、日志及备份都不会自动清理。备份含原始照片及元数据，应按自己的同步和隐私需求管理。
